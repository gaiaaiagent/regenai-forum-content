# The ChatGPT REST API Bridge: Democratizing Access

The Model Context Protocol is beautiful in its elegance. A standardized way for AI systems to discover tools, invoke capabilities, and orchestrate complex workflows. But elegance alone doesn't democratize access. MCP works natively with Claude Code, Claude Desktop, and the growing ecosystem of MCP-aware clients. What about the millions of users whose primary interface to AI is ChatGPT? What about organizations standardized on OpenAI's platform? What about the pragmatic reality that accessibility matters more than architectural purity?

This is where the REST API bridge enters the story. Not as a compromise, but as a translation layer that speaks the universal language of the web.

---

The `chatgpt_rest_api.py` file in the Registry Review MCP repository represents a particular kind of engineering decision: the recognition that protocols serve people, not the reverse. The file wraps the entire MCP server's functionality in a FastAPI application, exposing every tool as a standard HTTP endpoint. Create a session? POST to `/sessions`. Discover documents? POST to `/sessions/{session_id}/discover`. Extract evidence? The pattern continues. What was once a protocol-specific interface becomes accessible to any system that can make an HTTP request.

This matters because ChatGPT Custom GPTs operate through Actions—essentially, the ability to call REST APIs based on natural language requests. When a user tells the Registry Review Assistant GPT to "start a new review for Kulshan Carbon Trust," ChatGPT translates that intent into an HTTP POST to the appropriate endpoint, receives the structured JSON response, and presents it conversationally. The underlying MCP architecture remains intact. The tools, the session management, the workflow orchestration—none of that changes. What changes is the surface area for access. The same intelligence that powers Claude-based reviews now extends to ChatGPT users without any degradation in capability.

---

The file upload challenge reveals something deeper about the constraints of different AI platforms. MCP clients like Claude Code can handle file operations natively—reading from local filesystems, processing uploads, managing document storage. ChatGPT Custom GPTs lack this capability. They can make API calls, but they cannot directly transfer files from a user's computer to a remote server. This limitation could have been a dead end. Instead, it became an invitation for creative engineering.

The solution is a two-step upload pattern that elegantly sidesteps the constraint. First, the user (via ChatGPT) calls the `/generate-upload-url` endpoint. This returns a unique, time-limited URL where files can be uploaded directly from the browser. The user clicks the link, arrives at a clean HTML form with drag-and-drop functionality, uploads their project documents, and returns to ChatGPT with "I uploaded my files." ChatGPT then calls `/process-upload/{upload_id}`, which retrieves the pending uploads, creates or updates the review session, and runs document discovery. The workflow feels seamless to the user despite the technical gymnastics happening beneath the surface.

The HTML form itself is generated dynamically by the server, embedded directly in the Python code as a template string. This isn't elegant in the traditional software engineering sense—frontend code mixed with backend logic—but it's elegant in the pragmatic sense of minimizing deployment complexity. A single Python file serves both the API and the upload interface. No separate frontend build process. No additional hosting requirements. The form includes modern UX touches: drag-and-drop zones, file previews, progress indicators, clear instructions about returning to ChatGPT after upload. Every detail oriented toward reducing friction for users who may not be technical.

---

The bridge architecture reveals a pattern that extends beyond this specific implementation: MCP servers as backends for multiple frontend modalities. Consider what the Registry Review system now supports. Claude Code users connect directly via MCP, orchestrating multi-step reviews with full tool access and local file handling. ChatGPT users access the same capabilities through REST endpoints wrapped in a conversational Custom GPT interface. The Eliza agent framework can run autonomous review workflows through either protocol. A future web application could consume the same REST API with a custom UI. The same review logic, the same evidence extraction, the same cross-validation—expressed through whatever interface best serves each user's context.

This is the democratization that matters. Not lowest-common-denominator functionality, but full-capability access through multiple entry points. A registry reviewer who lives in ChatGPT all day shouldn't be forced to learn a new tool to benefit from AI-assisted review. A developer building custom workflows shouldn't be locked into a single AI provider. The REST API bridge creates optionality without sacrifice.

---

The technical implementation choices in `chatgpt_rest_api.py` reflect pragmatic wisdom accumulated through actual deployment. CORS middleware enables cross-origin requests from ChatGPT's domains. Pydantic models define request and response schemas that generate OpenAPI documentation automatically—documentation that ChatGPT can consume to understand available endpoints. The server configuration includes explicit URL patterns for the production endpoint, ensuring that generated upload links point to the right place. In-memory storage for pending uploads trades durability for simplicity in the current iteration, with clear comments noting where Redis or a database would be appropriate for production scale.

The status derivation system deserves attention. Sessions in the underlying MCP implementation track progress through a `workflow_progress` dictionary rather than a simple status field. But REST API consumers—especially conversational AI systems—benefit from human-readable status strings. The `get_derived_status()` function translates workflow progress into labels like "Initialized," "Documents Discovered," "Evidence Extracted," or "Completed." This translation layer exists purely for the benefit of ChatGPT's ability to communicate clearly with users. The underlying data model doesn't change; only the presentation adapts to the interface.

---

What emerges from this architecture is a template for multi-platform AI deployment in the regenerative economy. Build your core intelligence as an MCP server with well-designed tools and clear interfaces. Wrap that server in a REST API for universal HTTP access. Design upload workflows that accommodate platform limitations. Generate OpenAPI specifications that enable automated integration. The result is infrastructure that meets users where they are rather than demanding they come to you.

This matters for the broader mission of democratizing access to regenerative intelligence. The carbon registry review process shouldn't be accessible only to organizations with engineering resources to deploy custom AI tooling. A small land trust in Appalachia should have the same access to AI-assisted review as a well-funded environmental nonprofit. A project developer in Kenya should be able to use whatever AI platform is available to them. The REST API bridge doesn't just solve a technical problem—it embodies a commitment to accessibility that's core to the regenerative ethos.

The tragedy of silos isn't just about data. It's about capability. When powerful tools remain locked behind protocol barriers, expertise concentrates rather than distributes. The ChatGPT REST API bridge is one small contribution to a different pattern: infrastructure that creates conditions for emergence by expanding who can participate. Not everyone will use ChatGPT. Not everyone will use Claude. But everyone should have a path to the same intelligence.
