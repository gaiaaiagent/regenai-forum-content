# Breaking Down the Eight Stages in Detail

The Registry Review Agent workflow moves through eight distinct stages, each producing a discrete artifact that the human reviewer can verify before proceeding. This is not a rigid pipeline where automation replaces expertise; it is a collaborative rhythm, a dance between computational capacity and human judgment. Think of it as digestion: raw documents enter, get broken down, recombined, validated, and finally transformed into knowledge that can nourish the broader ecosystem. Each stage has its metabolism, its specific enzymes, its output that feeds the next.

## Stage 1: Initialize - The Intake Breath

Every living process begins with intake. The Initialize stage is the Registry Agent's first breath: it receives the project submission, establishes the review context, and creates the workspace where everything else unfolds. When a project proponent submits their carbon credit documentation, the agent creates a unique review session ID, accepts the uploaded files or links to cloud storage, and loads the appropriate checklist template based on the methodology. The agent generates Resource Descriptors for each file, capturing metadata like IRIs, checksums, and timestamps. The human's role here is architectural: they select the project, choose the data source mode (whether to mirror files locally or reference them in place), pick the right checklist template, and confirm that the session should proceed. The output is a session metadata record that becomes the foundation for everything that follows. Success means all required inputs are present, Resource Descriptors have valid checksums, and the session appears in the "Recent Reviews" list, ready for the next stage.

## Stage 2: Document Discovery - Sensing the Landscape

With the workspace established, the agent begins exploring what it has to work with. Document Discovery is the system's sensory apparatus: it scans the configured folders, extracts file metadata, normalizes file names, and classifies each document by type. Think of this as the agent walking through a forest and naming what it sees: here is a monitoring report, there is a land tenure deed, over there are the GIS shapefiles that define the project boundaries. The classification system distinguishes technical reports from legal documents, geospatial data from spreadsheets, images from unknowns. Each file gets a confidence score indicating how certain the agent is about its classification. The human reviewer then walks through this inventory, marking documents as In Scope, Ignored, or Pinned for critical context. Misclassifications get corrected. The stage succeeds when all files are scanned and classified with greater than 85% accuracy, and only the documents marked for inclusion flow forward. This creates a clean, organized document inventory, like a well-labeled specimen collection ready for analysis.

## Stage 3: Requirement Mapping - Building the Correspondence

Now the real cognitive work begins. Requirement Mapping is where the agent builds connections between what exists (documents) and what is needed (checklist requirements). The agent loads the machine-readable checklist template, parsing it into structured requirements with IDs, text descriptions, expected evidence types, and source citations back to the protocol. Then it analyzes the discovered documents using semantic matching, looking for conceptual relationships between document content and requirement language. For each requirement, the agent suggests which documents might contain relevant evidence, assigning confidence scores to each potential mapping. The human reviewer sees this as a matrix: rows are requirements, columns are documents, cells indicate suggested mappings. They confirm the high-confidence suggestions, remove incorrect mappings, and manually add connections the agent missed. Requirements with no plausible document matches get flagged for attention. The output is a mapping matrix where each requirement has a status: Suggested, Confirmed, Removed, or Unmapped. Greater than 90% of obvious mappings should be suggested correctly by the agent, with unmapped requirements clearly visible as warning icons demanding human attention.

## Stage 4: Evidence Extraction - The Digestion Process

With mappings established, the agent dives into the documents themselves. Evidence Extraction is the digestive phase: breaking down complex documents into the specific nutrients, the data points and text snippets, that will satisfy each requirement. For every requirement that has mapped documents, the agent parses the content through PDF text extraction, table recognition, and metadata parsing. It identifies relevant sections using the requirement context as a guide, then extracts zero to three evidence snippets per requirement. Each snippet includes a short quote or data point (two to three sentences maximum), source citation with document name, page number, and section, plus an extraction confidence score. Beyond snippets, the agent extracts structured data where applicable: dates (sampling dates, imagery dates, crediting periods), locations (coordinates, parcel IDs, field boundaries), ownership information (names, entities, deed references), and numerical data (areas, carbon values, sample counts). The human reviewer sees these extractions organized in collapsible panels for each requirement. They can delete irrelevant snippets, add manual notes alongside extracted evidence, request re-extraction for specific documents, or flag requirements where extraction seems incomplete. Success means greater than 85% of mapped requirements have at least one evidence snippet, all snippets include source citations, and false positives (snippets the reviewer disputes as irrelevant) stay below 5%.

## Stage 5: Cross-Validation - The Immune System

Here is where the agent's intelligence truly shines. Cross-Validation is the system's immune response: checking for consistency, completeness, and compliance across all extracted evidence. It operates on three levels. First, the Completeness Check verifies that each requirement has mapped documents and those documents contain expected evidence types, computing coverage status as Covered, Partially Covered, Missing, or Needs Manual Review. Second, the Consistency Validation cross-checks project metadata across documents (is the project name and ID consistent?), verifies that land tenure claims in the project plan match the deed documents, validates temporal alignment (sampling dates should fall within plus or minus four months of imagery dates), checks geolocation consistency (field boundaries should match across GIS files and reports), and confirms numerical consistency (areas, parcel counts, and sample counts should align). Third, Protocol Compliance checks methodology-specific requirements: stratification, sample depth, core counts, buffer pool contributions, leakage tests, additionality evidence, lab analysis including SOC percentage and accreditation. The agent generates validation flags at three levels: Info for notable non-blocking observations, Warning for potential issues requiring attention, and Error for clear requirement violations or critical gaps. The human reviewer sees a coverage summary ("34 of 50 covered, 10 partial, 6 missing"), can filter by status to focus on problems first, and can override agent assessments where expert judgment differs. Critical gaps get identified for proponent revision. The success criterion is that every requirement has a computed coverage status, consistency checks run for all applicable requirement pairs, and false positive validation errors (agent flags on non-issues) stay below 10%.

## Stage 6: Report Generation - The Synthesis

All the analysis now crystallizes into a structured artifact. Report Generation is the synthesis phase: compiling complete review findings into a Registry Review Report that serves as the authoritative record. The agent produces two representations: JSON for machine-readable audit trails and internal systems, plus a human-readable format (HTML, PDF, or Markdown) for sharing and archival. The report includes a header with project metadata, review date, reviewer, session ID, and checklist template. An executive summary provides coverage statistics, critical findings, and overall assessment. Per-requirement entries document the requirement ID and text, coverage status, mapped documents with their names and IRIs, evidence snippets with citations, validation flags and notes, and human annotations. A provenance section traces document sources, resolver URLs, checksums for verification, and access mode used. Appendices include the complete document inventory, validation logic applied (protocol version, methodology), and agent configuration and version. The report gets a version ID and timestamp, stored in the session reports collection. The human reviewer examines the generated report for completeness and clarity, can request regeneration if there are format issues or missing sections, and exports in their preferred format. Success means all requirements appear with complete data, all citations resolve to actual documents and locations, the provenance section enables independent verification, and the human-readable format is clear and professional.

## Stage 7: Human Review - The Expert Eye

This is where human expertise takes center stage. Human Review is the validation layer where expert judgment engages with everything the agent has prepared. The agent presents the report in an editable interface, tracking all human edits with timestamps and attribution. It supports revision workflows: marking requirements as Pending Proponent Revision, accepting revised or additional documents, and re-running relevant stages for updated materials. A change log maintains complete documentation of all modifications. The human reviewer examines the complete report with a critical eye. They edit narrative sections and notes, override agent assessments using their expertise, and identify items requiring proponent revision: missing documents, insufficient evidence, inconsistencies needing explanation, or protocol requirement violations. If revisions are needed, the reviewer requests them from the proponent, uploads or links revised documents when they arrive, and re-runs affected workflow stages. Finally, the reviewer makes the final determination: Approve (project meets requirements, ready for completion), Conditional Approval (minor fixes needed, can proceed with notes), Reject (major gaps requiring substantial rework), or On Hold (awaiting information, cannot assess yet). Success means all requirements have human-verified status, the reviewer can clearly articulate their approval rationale or rejection reasons, revision workflows handled smoothly without data loss, and the change log provides a complete audit trail.

## Stage 8: Completion - The Exhalation

The final stage closes the loop. Completion is the exhalation that prepares the review for archival and on-chain registration. The agent locks the finalized report to prevent further edits without creating a new version. It generates the final report package: approved Registry Review Report in PDF and JSON formats, complete document inventory with checksums, audit trail capturing all changes, re-runs, and human decisions, plus provenance metadata for all resources. For on-chain registration, it prepares project metadata ready for the Regen Ledger, document IRIs for data module anchoring, and a review attestation signed by the reviewer. Session materials get archived: all uploaded documents (if Mirror mode was used), complete review history, and communication logs. The human reviewer provides final sign-off, submits the project for on-chain registration if approved, communicates the final decision to the proponent, archives materials according to organizational standards, and notes lessons learned for future reviews. The output is a finalized review package with locked report and complete audit trail, on-chain registration data (if approved) including project instantiation parameters, document IRI anchors, and review attestation hash, plus a session closure record with final status, completion timestamp, and reviewer sign-off. The session status updates to Completed, and the workflow concludes.

## The Living Flow

These eight stages are not a rigid assembly line. They form a living process with feedback loops and branching paths. After Document Discovery, new documents can trigger re-discovery. After Requirement Mapping, document changes can trigger remapping. After Evidence Extraction, specific requirements can be re-extracted. After Cross-Validation, critical gaps can branch to revision workflows. After Report Generation, major gaps discovered during review can return the process to earlier stages. After Human Review, revisions received can restart partial workflows. The system supports surgical re-execution: a new document triggers re-discovery, which updates only the stages affected by that document. This is not waterfall development applied to document review. It is a responsive, adaptive process that mirrors how living systems actually work: sensing, responding, adjusting, synthesizing, and finally reaching a stable state.

The agent handles the tedious: scanning thousands of pages, cross-referencing dates across documents, flagging inconsistencies in owner names. The human brings what no model can: contextual understanding, expert judgment, the wisdom to know when a minor discrepancy matters and when it does not. Together, something emerges that neither could achieve alone. This is the vision we are building toward: not AI that replaces human expertise, but AI that partners with it, creating conditions where both can do what they do best. The eight stages are the structure. The collaboration is the life that flows through it.
