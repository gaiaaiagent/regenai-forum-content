# Nuances of the Implementation

Every system carries the fingerprints of its makers. Look closely at any well-designed infrastructure and you'll find embedded decisions that reveal worldviews, priorities, tensions navigated in the quiet hours of development. The Registry Review MCP is no exception. Beneath its eight-stage workflow and clean API surface lies an architecture of trade-offs, each one a small philosophical statement about what matters when you're building tools for regeneration. This is the story of those nuances: the dual-track extraction, the semantic matching, the cross-validation logic, and the quiet machinery of session state that makes it all cohere.

## The Dual-Track Philosophy: Fast Enough and Good Enough

Consider the problem of PDF extraction. Project documents arrive in all formats, but PDFs dominate the registry workflow: land tenure certificates, baseline monitoring reports, project plans dense with tables and figures. The question isn't whether to extract text from PDFs; it's *how*, and the answer reveals a design philosophy. We could have built a single extraction pipeline and called it done. Instead, the system implements what we call *dual-track extraction*: a fast path using PyMuPDF for rapid text extraction, and a high-quality path using Marker for documents where precision matters more than speed. The fast extractor rips through documents in milliseconds, extracting text good enough for initial classification and search. The Marker path takes longer but preserves table structures, handles complex layouts, and produces markdown that retains the semantic organization of the original. This isn't redundancy; it's *emergence through optionality*. When a document enters Stage 2 (Document Discovery), the fast extractor handles initial classification. But when Stage 4 (Evidence Extraction) needs to pull specific data points from a monitoring report with nested tables showing soil organic carbon measurements over time, the system can invoke the high-quality path. The trade-off is explicit: speed when speed matters, quality when quality matters. Neither alone would serve the regenerative workflow; together, they create conditions for appropriate response.

## Semantic Matching: When Fuzzy Is a Feature

Traditional document management systems rely on exact matching. A requirement maps to a document because someone manually tagged it that way, or because a filename follows a rigid convention. But regenerative projects don't work that way. A soil carbon methodology might accept evidence from documents variously titled "Baseline Assessment," "Initial Soil Survey," "Pre-Project Monitoring Report," or simply "Soil_Data_2023.pdf." The Registry Review MCP handles this through semantic matching with confidence scoring: a requirement like "REQ-002: Land Tenure" doesn't need an exact document name match. Instead, the system infers document types from categories and keywords, matching "land tenure" requirements to documents classified as legal documents, land deeds, or project plans that might contain tenure information. The `_infer_document_types` function builds this bridge, mapping requirement categories to lists of plausible document classifications. When it encounters "baseline" in the requirement text, it suggests baseline reports and project plans. When it sees "GIS" or "shapefile," it looks for geospatial data. This fuzzy matching cascades through the system. In cross-validation, owner names like "John Smith" and "John D. Smith" need to be recognized as the same person across documents. The validation tools use fuzzy string matching with an 80% similarity threshold, with special handling for surname matching that boosts confidence when last names align even if full names differ slightly. This is the kind of nuance that only matters in practice: real project documents contain real human inconsistencies, OCR errors, naming variations. A system built for laboratory conditions would fail in the field. We built for the field.

## Citation Verification: Trust, But Verify

Here's the uncomfortable truth about large language models: they hallucinate. They confidently assert facts that exist nowhere in the source documents. When you're using LLMs to extract evidence from project documentation, this isn't a minor inconvenience; it's a fundamental integrity problem. A land tenure claim that doesn't appear in the source documents could undermine the entire credit verification process. The verification module addresses this with what we call *citation verification through fuzzy text matching*. When the LLM extraction reports that it found "Project Start Date: 01/01/2022" in a document, the verification system goes back to the source content and looks for that text. If it finds an exact match, confidence stays high. If it can't find anything similar (below a 75% fuzzy match threshold), the system doesn't just flag the field; it *penalizes the confidence score* and attaches a verification warning. This creates a chain of accountability. Every extracted field carries a `verification_status` ("verified" or "failed"), a `verification_score` (the best fuzzy match percentage), and optionally a `verification_warning` explaining why confidence was reduced. The human reviewer doesn't just see the extracted data; they see whether that data actually exists in the documents. The sliding window approach in the verification function is particularly elegant. Rather than looking for exact substring matches, it moves through the source document comparing overlapping windows of text, using token-set ratio matching that handles word order differences and minor variations. This catches the real-world case where an LLM extracts "The project start date is January 1, 2022" but the document says "January 1, 2022 marks the project commencement." Different words, same truth, verified.

## Cross-Validation: Consistency Across Documents

A single document can contain internally consistent lies. Truth emerges from triangulation: comparing claims across multiple sources, checking that dates align, verifying that the landowner name in the tenure document matches the name in the project plan. The cross-validation stage (Stage 5) implements three types of consistency checks, each revealing assumptions about what matters in regenerative credit verification. Date alignment validation compares temporal claims across documents. If a project plan says the start date is January 2022 and a baseline report shows sampling in March 2023, are these consistent? The system allows a configurable `max_delta_days` (default 120) between related dates, flagging pairs that exceed this threshold. The logic is simple but the implication is profound: we're not just checking that dates exist, we're checking that the narrative holds together across documents. Land tenure validation goes deeper, using fuzzy matching on owner names with enhanced surname checking. If one document lists "Maria Garcia" and another lists "M. Garcia," the system recognizes these as likely the same person. But it also checks area consistency (allowing 5% variance for rounding differences) and tenure type consistency. A mismatch between "freehold" in one document and "leasehold" in another triggers a validation failure; that's not a typo, that's a potential problem. Project ID validation ensures consistent identification across the document set. The system expects project IDs to appear in at least three documents and to follow expected patterns (like "C02-1234" format). When multiple project IDs appear, or when the ID appears in too few documents, the validation flags it for review. This catches the subtle error where two projects' documents accidentally got mixed together.

## Session State: The Quiet Machinery of Continuity

Perhaps the least visible but most essential infrastructure is session state management. A registry review isn't a single API call; it's a multi-stage workflow that might span hours or days, with human reviewers stepping away and returning, with documents added mid-process, with mappings confirmed incrementally. The StateManager class handles this through a simple but robust pattern: JSON files in a session directory, with atomic read-write operations and automatic migration support. When the workflow evolved from seven stages to eight (adding Requirement Mapping as a distinct step), the system needed to handle sessions created under the old model. The migration logic in `migrate_workflow_progress` demonstrates the thoughtfulness embedded throughout: existing sessions automatically gain the new `requirement_mapping` field, with intelligent inference (if evidence extraction is complete, assume mapping was done). Immutability in the settings singleton deserves mention. After a data loss incident in December 2025 where test fixtures accidentally modified production settings, the Settings class was made immutable post-initialization. Any attempt to modify settings after `__init__` raises a TypeError. This is defensive programming for systems that matter: the paths where production data lives should never be changeable at runtime, period. The XDG Base Directory Specification compliance might seem like a minor detail, but it reflects care about where things live. Sessions go to `~/.local/share/registry-review-mcp/sessions/`, cache to `~/.cache/registry-review-mcp/`. This structural separation means test code literally cannot delete production sessions; they're in different directories, isolated by design. Infrastructure choices are ontological choices. Where you store data shapes what becomes possible.

## The Trade-offs We Accept

No design is without compromise. The dual-track extraction adds complexity. The fuzzy matching can occasionally match things that shouldn't match. The LLM extraction costs money with every API call. We accept these trade-offs because the alternatives are worse. The complexity of dual-track extraction is complexity in service of appropriate response. The fuzzy matching failures are rarer than the strict matching failures we'd see otherwise. The LLM costs are budgeted against the human hours saved. And we've built in safeguards throughout. Confidence thresholds filter low-quality extractions. Citation verification catches hallucinations. Human review remains the final stage, not because we distrust the automation, but because we respect the stakes. These are carbon credits representing real land, real farmers, real atmospheric impact. The system augments human judgment; it never replaces it.

## Building for Emergence

What does it mean to build tools for regeneration? It means accepting that the system will be used in ways you can't predict, by people solving problems you haven't imagined. It means creating *surface area for emergence*: not rigid pipelines but flexible tooling that adapts to context. The eight-stage workflow is a scaffold, not a cage. The confidence scores are guidance, not verdicts. The verification warnings are invitations for human attention, not roadblocks.

This is Week 4 of building the Registry Review MCP. The architecture is settling. The nuances are becoming features. And every time Becca runs a project through the system and something unexpected works, we learn what matters. The farm cooperative in Czech Republic with 111 projects waiting for review, they don't need perfect software. They need software that helps imperfect humans make better decisions faster. That's the nuance we're building for. The clever engineering serves the humble purpose.
