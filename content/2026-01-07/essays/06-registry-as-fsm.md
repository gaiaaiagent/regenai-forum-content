# The Registry Assistant as Finite State Machine

There is something deeply satisfying about a finite state machine. In computer science, an FSM is a mathematical model of computation where a system exists in exactly one state at any given time, transitions between states follow strict rules, and the system progresses deterministically from an initial state toward completion. When I first started building the Registry Review Agent, I did not set out to implement an FSM. But as the architecture emerged through conversations with Becca, Gregory, and the broader Regen team, the pattern became undeniable. What we were building was not a chatbot that might occasionally help with document review. We were building a machine with discrete states, defined transitions, and clear completion criteria. We were building Mario, trying to reach level eight.

That analogy came to me during a walkthrough session with Becca. Each review session progresses through eight carefully designed stages, a journey I likened to playing Mario. In the classic game, you cannot skip from World 1-1 to World 8-4. You must progress through each level, each world, accumulating power-ups and capabilities along the way. The Registry Agent works identically. You cannot cross-validate evidence before you have extracted evidence. You cannot extract evidence before you have mapped requirements to documents. You cannot map requirements before you have discovered what documents exist. The linear progression is not a limitation; it is the fundamental architecture that makes the system reliable, auditable, and trustworthy. Every stage produces artifacts that the human reviewer can verify before proceeding, and each stage depends absolutely on the successful completion of what came before.

The eight stages form a coherent progression that mirrors how an expert actually thinks about document review. Stage One is Initialize: assign a project ID, load the methodology checklist, confirm we are working from the correct version of requirements. Stage Two is Document Discovery: scan the uploaded folder, classify each file by type, normalize filenames, and create an inventory of what we have to work with. Stage Three is Requirement Mapping: connect the 23 checklist requirements for soil carbon verification to the specific documents that might contain evidence for each. Stage Four is Evidence Extraction: actually open those documents, parse the PDFs, extract the specific snippets and data points that satisfy each requirement. Stage Five is Cross-Validation: check that dates align across documents, that ownership claims match deed records, that project IDs are consistent, that the story told by one document does not contradict the story told by another. Stage Six is Report Generation: compile all findings into structured output, both human-readable markdown and machine-readable JSON, with complete citations and provenance. Stage Seven is Human Review: present the automated findings to an expert reviewer who can override assessments, request revisions, and make final determinations. Stage Eight is Completion: lock the report, archive the session, and prepare data for on-chain registration.

The state machine metaphor extends beyond simple linear progression. Each stage has defined transition rules that determine what happens next, and these rules include branches and loops, not just forward movement. After Document Discovery, if critical file types are missing, the system does not blindly proceed. It flags the gap and blocks progression until the proponent supplies the necessary documentation. After Requirement Mapping, if more than fifty percent of requirements remain unmapped, the system escalates with a warning that perhaps the wrong checklist was selected. After Cross-Validation, if critical gaps are identified, the workflow branches into a revision loop where the human reviewer can send requests back to the proponent, receive updated documents, and re-run affected stages without starting from scratch. The FSM architecture makes all of this explicit, auditable, and predictable. When you are sitting at Stage Five and a validation check fails, you know exactly what options exist: proceed anyway with a warning flag, return to Stage Four for re-extraction, or branch into the revision workflow. There is no ambiguity, no hidden state, no mystery about what the system might do next.

The practical implications of this architecture become clear when you consider the alternative. A less structured approach might allow the AI to skip between tasks opportunistically, perhaps extracting some evidence, then validating something, then discovering a new document, then circling back to extract more. Such flexibility sounds appealing in the abstract, but it creates chaos in practice. How do you know what has been validated? How do you audit the process? How do you resume a partially completed review after your computer crashes? The FSM answers all of these questions definitively. Session state is persisted in JSON files with atomic write operations and file locking to prevent corruption. Each stage completion is timestamped and logged. The current stage is always knowable by examining the session record. When Becca closes her laptop on Friday and opens it Monday morning, the system knows exactly where she left off. When the Anthropic API returns an error during evidence extraction, the system knows exactly which requirements have been processed and which remain. The state machine is not just a conceptual model; it is the literal implementation that makes the whole system reliable.

Perhaps the deepest insight from building the Registry Agent as an FSM is how naturally it enables human-AI collaboration. The collaboration model specifies that AI writes in blue while humans write in black. Every stage includes human verification checkpoints. But this collaboration only works because the state machine creates clear handoff points. The agent processes documents and suggests mappings; the human confirms or corrects those mappings before the system proceeds. The agent extracts evidence and generates validation flags; the human reviews those flags and exercises expert judgment. The agent produces a structured report; the human reads it, annotates it, and makes the final determination. Each handoff is explicit, each transition requires acknowledgment, each stage creates a natural pause for human oversight. This is not AI replacing human judgment. This is AI augmenting human capacity by handling the tedious cross-referencing that currently consumes hours, freeing the expert to focus on the decisions that actually require expertise. The FSM architecture is what makes this partnership legible, auditable, and ultimately trustworthy. When a carbon credit project gets registered on-chain, there is a complete audit trail showing exactly how the system progressed through each stage, what the agent found, what the human decided, and why the final determination was made. That is not just good engineering; it is the foundation for regenerative verification at planetary scale.
