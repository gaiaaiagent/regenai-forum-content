# The Regen Registry Assistant Architecture: MCP and OpenAPI for ChatGPT

The Model Context Protocol was designed for Claude. That was the starting assumption, and for good reason: Anthropic built MCP as the native interface between their AI systems and external tools. But the regenerative economy does not belong to any single platform. Project developers use ChatGPT. Registry analysts work in Claude Code. Autonomous agents run on Eliza. If we built tools that only worked with one AI system, we would be building walls in an ecosystem that desperately needs bridges. So we asked a different question: What if we could take the same intelligent workflow and make it accessible everywhere? What if the same review logic that powers Claude Code sessions could also power a ChatGPT Custom GPT? The answer lives in a file called `chatgpt_rest_api.py`, and it represents something I believe will become a pattern across the emerging AI tool ecosystem: the MCP-to-REST bridge. This architecture democratizes access to intelligent workflows by wrapping protocol-native tools in the lingua franca of the web.

The core insight is deceptively simple. ChatGPT Custom GPTs interact with external services through Actions, which are nothing more than REST API calls defined by an OpenAPI specification. You give ChatGPT a schema that describes your endpoints, their parameters, and their response formats. When a user asks the Custom GPT to perform a task, it translates natural language into the appropriate API call, sends the request, and renders the response. This is exactly what MCP does for Claude, just with different protocol mechanics. MCP uses JSON-RPC over stdio or HTTP; ChatGPT Actions use standard REST over HTTPS. MCP defines tools with input schemas and returns structured content blocks; REST APIs define endpoints with request bodies and return JSON responses. The structures are isomorphic. They are different expressions of the same fundamental idea: give an AI system structured access to external capabilities. Our `chatgpt_rest_api.py` exploits this isomorphism. It imports every tool module from the Registry Review MCP, defines FastAPI endpoints that correspond to each tool, and translates between the REST request format and the internal tool invocation. When ChatGPT calls `POST /sessions/{session_id}/discover`, the FastAPI handler calls the same `discover_documents()` function that Claude invokes through MCP. Same logic, different transport. The AI does not know or care which protocol delivered the request; it receives structured data and returns structured results.

The implementation reveals fascinating details about what it means to bridge protocols. Consider the file upload workflow, which presented our most interesting architectural challenge. MCP clients like Claude Desktop can pass file content directly as base64-encoded strings in tool parameters. The model reads a file, encodes it, and includes it in the tool call. But ChatGPT Actions cannot do this. When a user uploads a file to a ChatGPT conversation, that file lives in OpenAI's infrastructure, not accessible to external API calls. The Custom GPT cannot simply send you the file bytes because it does not have a way to reference them in an HTTP request body. Our solution is what I call the two-step upload pattern. When a user wants to start a review with uploaded documents, ChatGPT calls our `/generate-upload-url` endpoint, which creates a unique upload session, generates a secure token, stores pending session metadata in memory, and returns a URL. The Custom GPT then instructs the user to click this link and upload their files directly through a browser form. We serve a full HTML page with drag-and-drop file handling, progress indicators, and a success message that tells the user to return to ChatGPT. Once files are uploaded, the user tells ChatGPT they are ready, and ChatGPT calls `/process-upload/{upload_id}` to trigger the actual session creation and document discovery. Two steps instead of one, but the workflow remains smooth and the user barely notices the handoff.

The two-step pattern teaches something important about AI system design. Different platforms have different capabilities, and rather than accepting the lowest common denominator, you can design workflows that gracefully accommodate those differences. Claude gets direct file upload through MCP's base64 encoding. ChatGPT gets a web-based upload flow that feels native to how humans already interact with file upload systems. Eliza agents can use either pathway depending on how they are deployed. The underlying business logic is identical; only the entry point differs. This is not a workaround or a hack. It is a principled architecture that recognizes heterogeneity as a feature of the ecosystem rather than a bug to be eliminated. We serve multiple client types without duplicating code, without maintaining separate implementations, without fragmenting the development effort. Every improvement to the core review workflow benefits every platform simultaneously because every platform ultimately calls the same functions.

The FastAPI server itself is a study in protocol translation. Each endpoint definition maps directly to an MCP tool, with request models that mirror tool input schemas and response structures that preserve all the information the tools return. The server adds CORS headers to allow browser-based requests from ChatGPT's domain. It defines Pydantic models that FastAPI uses to auto-generate OpenAPI documentation, which means we get our Action schema for free simply by visiting the `/docs` endpoint. The deployment architecture puts this REST API behind a reverse proxy at `https://regen.gaiaai.xyz/registry`, making it accessible to any ChatGPT Custom GPT or other HTTP client. The same server that handles ChatGPT requests could handle requests from a mobile app, a web dashboard, a Slack bot, or any other system that speaks HTTP. MCP remains the native interface for Claude-family clients; REST remains the native interface for everything else. Both interfaces call the same Python functions. Both interfaces benefit from the same testing, the same bug fixes, the same improvements. This is not duplication; it is multiplication. We write the workflow once and expose it through every relevant protocol.

The deeper implication of this architecture is about access and democratization. The regenerative economy needs AI tools that work for everyone, not just those who happen to use the right AI platform. A project developer in Colombia might prefer ChatGPT because that is what they learned first. A registry analyst in Oregon might live in Claude Code because that is what integrates with their development workflow. A community manager in Kenya might access these tools through a WhatsApp integration running on Eliza. None of these preferences should determine whether they can benefit from intelligent registry review workflows. By maintaining the MCP server as the source of truth and exposing it through multiple protocol adapters, we ensure that platform choice becomes a matter of preference rather than capability. The same intelligent workflow that helps Becca process project submissions in Portland helps a developer in Bogota understand what documentation they need to prepare. The same cross-validation logic that catches inconsistencies for experts catches them for newcomers. The architecture is a statement of values as much as a technical decision: intelligence should be accessible, tools should meet users where they are, and the regenerative economy should not be gated by which AI provider you happen to prefer. MCP and REST are not competing protocols; they are complementary channels into the same pool of capability. Build once, deploy everywhere. That is the promise of the dual architecture, and it is the foundation upon which we are building tools that can actually scale to planetary need.
